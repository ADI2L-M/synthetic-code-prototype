# Synthetic code calibration: implementation audit

## Scope and evidence standard

**Verified** means the behavior follows from the current executable call path and is corroborated where a relevant test exists. **Partially Verified** means the mechanism is present, but its intended effect on generated code or empirical fidelity is not established by repository evidence. **Not Verified** means the claimed mechanism is absent from the inspected execution path or no current-run evidence establishes it. This audit inspected code, configuration, tests, and aggregate experiment records. It did not execute authentic submissions or start an LLM run.

The CLI experiment path is the subject of the algorithm below. The interactive single-batch entry point, `run_prototype_iteration`, also calls `run_iteration`, but it does not itself run a calibration loop ([`prototype_runner.py` lines 20–59](../services/generation/prototype_runner.py#L20)).

## End-to-end algorithm and call chain

**Verified.** `scripts/run_generation_experiment.py:main` reads the selected task's empirical `target_profile` and computes each available target standard error as `standard_deviation / sqrt(eligible_tasks)`. It constructs `ExperimentConfig`, then calls `run_experiment` with an `OllamaProvider` factory ([`run_generation_experiment.py` lines 17–35, 38–107](../scripts/run_generation_experiment.py#L17)). The upstream exporter constructs each target from the mean prevalence over eligible authentic tasks and omits unavailable values ([`target_profile.py` lines 15–58](../services/research/target_profile.py#L15)). The CLI does not recompute this profile from authentic submissions.

**Verified.** The full runtime chain is:

1. `main` → `_profile_inputs` → `ExperimentConfig` → `run_experiment` ([`run_generation_experiment.py` lines 17–107](../scripts/run_generation_experiment.py#L17)).
2. `run_experiment` → `load_prototype_task` → `run_iteration`, once for each condition and repetition, and up to `max_iterations` for the iterative condition ([`experiment.py` lines 344–399](../services/generation/experiment.py#L344)). Task contracts and evaluator cases come from `generation_configuration.json` through `load_prototype_tasks` ([`prototype_tasks.py` lines 11–34](../services/generation/prototype_tasks.py#L11); [`generation_configuration.json` lines 3–62](../config/generation_configuration.json#L3)).
3. `run_iteration` → `build_generation_specification` or `build_baseline_specification`; `plan_defect_assignments`; for each guided submission, `_mandatory_category_assignments` and `build_submission_specification` ([`workflow.py` lines 240–299](../services/generation/workflow.py#L240)).
4. For each generation or repair attempt: optional provider `build_prompt` → provider `generate(task, 1, seed, specification)` → `validate_source` → research or core defect detector → `_repair_quality`; if needed, `_repair_specification` and another attempt ([`workflow.py` lines 317–451](../services/generation/workflow.py#L317); [`ollama.py` lines 110–167, 169–222](../services/providers/ollama.py#L110)).
5. `observed_profile` and `observed_counts` → `compare_profiles` → `IterationResult` ([`workflow.py` lines 475–506](../services/generation/workflow.py#L475); [`analysis.py` lines 8–32, 55–125](../services/generation/analysis.py#L8)).
6. In the iterative condition, `IterationResult.accepted`, `calibration_is_non_regressive`, `_profile_selection_key`, and `calibration_constraints` determine stopping, selection, and the next iteration's constraint strings. `append_experiment_log` stores summary data ([`experiment.py` lines 256–274, 277–312, 400–454](../services/generation/experiment.py#L256)).

The three conditions are a task-only non-adaptive baseline, a task-aware single iteration, and a task-aware iterative run. Only the last performs feedback calibration. The initial task-aware conditions share a seed namespace for matched initial draws; later iteration numbers change the assignment and generation seeds ([`experiment.py` lines 364–397](../services/generation/experiment.py#L364); [`workflow.py` lines 264–270, 300–305](../services/generation/workflow.py#L264)). **Verified.**

## A. Defect assignment

**Verified — target to plan.** For defect *d* and batch size *B*, the planner records expected count `E_d = target_d × B`. Its planned integer count is `floor(E_d) + Bernoulli(frac(E_d))`, using a per-defect deterministic pseudo-random seed derived from the task, iteration, optional namespace, and defect. This is stochastic rounding of a batch quota, not an independent Bernoulli trial for each submission ([`assignment.py` lines 23–65](../services/generation/assignment.py#L23)). Tests check reproducibility and preservation of rare fractional expected counts ([`test_assignment.py` lines 6–39](../tests/unit/services/test_assignment.py#L6)).

**Verified — joint placement.** Defects are placed in descending target prevalence. For each defect, submissions are ordered by current assignment load with seeded random tie breaks; the planner places the requested count in the least loaded submissions, allowing co-occurrence. The planner caps *planned* defects at three per submission and raises `ValueError` if a quota cannot fit. There is no pairwise incompatibility matrix or joint probability model in this planner ([`assignment.py` lines 70–115](../services/generation/assignment.py#L70)). Per-defect quota draws are separate, but placement couples defects through load and capacity. **Not Verified — incompatible-combination enforcement:** no executable incompatibility check was found in this path.

**Verified — mandatory category overlay.** In guided conditions, the workflow also chooses one task-independent and one task-dependent defect from the task-applicable catalog. It sorts by calibration priority (`strengthen`, `maintain`, `reduce`), then configured reliable-defect order, target prevalence, and name; it cycles through that ordered list by submission ID. It unions these two choices with the quota plan, removing duplicate names ([`workflow.py` lines 183–218, 285–299](../services/generation/workflow.py#L183); [`generation_configuration.json` lines 144–160](../config/generation_configuration.json#L144)). Thus zero-target defects can still be assigned, the final assignment can exceed the planner's three-defect cap, and final per-defect assignment counts can exceed the recorded `planned_assignment_counts`. A unique preferred-order position generally decides before target prevalence is used as a tie breaker. The tests establish that planned assignments are included in final assignments, not that final counts equal quotas ([`test_prototype_generation.py` lines 166–181](../tests/unit/services/test_prototype_generation.py#L166)).

**Partially Verified — eligibility.** Runtime prompt categories use catalog `category` and `applicable_tasks` ([`configuration.py` lines 67–83](../services/generation/configuration.py#L67); [`defect_specifications.json` lines 88–109, 322–380](../config/defect_specifications.json#L88)). The research eligibility service classifies `eligible`, `not_applicable`, or `instruction_confounded` via a separate matrix, and the research pipeline calls it upstream ([`eligibility.py` lines 17–46](../services/research/eligibility.py#L17); [`pipeline.py` lines 40–47](../services/research/pipeline.py#L40)). `run_iteration` passes the input target mapping directly to the quota planner and does not call `eligibility_for` or reject a target key that is inapplicable to the selected task ([`workflow.py` lines 252–270](../services/generation/workflow.py#L252)). Consequently eligibility relies on the supplied empirical profile and configuration agreeing; runtime enforcement of target-key eligibility is **Not Verified**. Quota planning itself validates prevalence range and batch/capacity inputs, but not task applicability ([`assignment.py` lines 45–50](../services/generation/assignment.py#L45)).

**Verified — calibration influence.** Calibration never changes the prevalence values passed to `plan_defect_assignments`; it changes the priority order of the mandatory category overlay. A change to one defect can move it ahead of another, changing assignments of other defects. Re-seeding on each iteration also changes placements even with an unchanged target. There is no updated sampling probability or weight ([`experiment.py` lines 383–389, 424–426](../services/generation/experiment.py#L383); [`workflow.py` lines 201–217, 264–270](../services/generation/workflow.py#L201)).

## B. Generation, validation, and observed prevalence

**Verified.** The task-level guided specification lists functional requirements, applicable defect categories, and calibration actions, but deletes/ignores its `target` argument. The actual initial guided provider call receives the *per-submission* specification, which names every assigned style, gives configured hints, observable signatures, examples, task-specific patterns, unassigned-style avoidance advice, functional cases, and calibration text. The task-level `IterationResult.specification` is a record and is not the initial guided prompt sent by `run_iteration`. The baseline receives a task-only specification. Ollama adds common task tests and output instructions around whichever specification is supplied ([`prompt_builder.py` lines 48–85, 88–98, 101–245](../services/generation/prompt_builder.py#L48); [`workflow.py` lines 245–249, 295–299, 327–362](../services/generation/workflow.py#L245); [`ollama.py` lines 169–222](../services/providers/ollama.py#L169)). The fixed task contract, functional tests, defect catalog, hint templates, output contract, target profile, batch size, and tolerance are not rewritten by calibration; selected defect lists and calibration text can vary. **Partially Verified:** the prompt instructions are executable inputs to an LLM, but their effect on model behavior is not guaranteed by the implementation.

**Verified.** `validate_source` first rejects listed unsafe AST constructs, then invokes a timed Python subprocess in a temporary directory with the generated source, required function name, and configured test cases. The runner compiles and executes the source, invokes the function on each case, checks expected value, optional exact type, or expected exception, and returns `PASS` only if all cases pass. Syntax/runtime errors and timeout produce `FAIL` ([`validator.py` lines 31–109](../services/generation/validator.py#L31); [`validation_runner.py` lines 25–74](../services/generation/validation_runner.py#L25)). This is correctness against the configured finite evaluator cases, not a proof of functional correctness for all inputs. **Partially Verified — general functional correctness.**

**Verified.** Detection runs only for functionally passing attempts. It uses research detectors when all requested IDs belong to the research registry, otherwise the core registry. For guided runs the detection list is the union of target keys and all task-applicable defect names ([`workflow.py` lines 43–52, 252–263, 367–403](../services/generation/workflow.py#L43)). A passing output is checked for at least one defect from each category, every assigned defect, and any detected but unassigned style. If any requirement remains, or functional validation fails, the next attempt receives a revision request with prior source, failure details, missing and unexpected styles, and repair instructions. The repair specification is rebuilt from these facts and does **not** include the previous iteration's calibration section directly ([`workflow.py` lines 106–180, 381–441](../services/generation/workflow.py#L106)). The repair still carries the assigned defects. The first attempt with perfect functional and style compliance stops retries; otherwise the best attempt is retained by a lexicographic quality tuple prioritizing `PASS`, then fewer unresolved requirements, with earlier attempt winning ties ([`workflow.py` lines 80–104, 405–465](../services/generation/workflow.py#L80)).

**Verified.** Every submission slot yields one retained `SubmissionResult`, including a retained `FAIL` after exhausting retries. Observed defect prevalence is `detected_count / number_of_PASS_submissions`; failures are excluded, while passing submissions count even when assigned defects or category requirements are missing or unexpected defects are present. The `category_requirements_met` flag is stricter than this prevalence denominator ([`workflow.py` lines 443–485](../services/generation/workflow.py#L443); [`analysis.py` lines 8–32](../services/generation/analysis.py#L8)). This denominator behavior is tested ([`test_workflow.py` lines 109–118](../tests/integration/test_workflow.py#L109)). If no submission passes, observed prevalence is zero and observed denominator is zero; comparison falls back to target-relative tolerance. There is no minimum valid-count or minimum functional-pass-rate gate before comparison or iteration acceptance ([`analysis.py` lines 11–17, 39–40, 84–102](../services/generation/analysis.py#L11); [`types.py` lines 95–97](../models/types.py#L95)). **Not Verified — insufficient-batch rejection.** A provider returning no source for a slot, a detector exception, or a cancellation aborts rather than creating a reduced batch ([`workflow.py` lines 273–275, 357–379](../services/generation/workflow.py#L273)).

## C. Exact discrepancy-to-calibration mechanism

**Verified.** For each target defect, `difference = target − observed`. With a positive valid denominator, the observed 95% Wilson interval supplies an approximate standard error `(upper − lower)/(2 × 1.96)`. The decision margin is the larger of `abs(target) × tolerance` and `1.96 × sqrt(target_standard_error² + observed_standard_error²)`. A positive difference above the margin is `Underrepresented/Increase`; a negative difference below the negative margin is `Overrepresented/Reduce`; otherwise it is `Within tolerance/Maintain`. With zero denominator, the margin is only `abs(target) × tolerance` ([`analysis.py` lines 35–52, 55–125](../services/generation/analysis.py#L35)). The workflow passes both valid counts and the CLI-loaded target standard errors ([`workflow.py` lines 477–485](../services/generation/workflow.py#L477); [`run_generation_experiment.py` lines 28–35](../scripts/run_generation_experiment.py#L28)). Tests cover the signed action, small-sample Wilson margin, large gap, and zero detected count ([`test_workflow.py` lines 120–177](../tests/integration/test_workflow.py#L120)).

**Verified.** `calibration_constraints` maps each comparison action to a literal string: `Increase → strengthen the generation constraint`, `Reduce → reduce the generation constraint`, and `Maintain → maintain the generation constraint`. The next iteration inserts these strings into `CALIBRATION ADJUSTMENTS` in each guided submission specification, and `_mandatory_category_assignments` uses them as sort priorities. No numeric adjustment size, proportional controller, updated quota, or updated target is implemented ([`calibrator.py` lines 4–12](../services/generation/calibrator.py#L4); [`prompt_builder.py` lines 48–60, 229–230](../services/generation/prompt_builder.py#L48); [`workflow.py` lines 201–217, 295–299](../services/generation/workflow.py#L201); [`experiment.py` lines 383–389, 424–426](../services/generation/experiment.py#L383)). The next constraint mapping is computed from the **latest** iteration's comparison even if that iteration is not selected as the best result. The original `config.target_profile` is passed again each time and copied into each iteration result ([`experiment.py` lines 383–389, 418–426](../services/generation/experiment.py#L383); [`workflow.py` lines 487–504](../services/generation/workflow.py#L487)).

**Partially Verified — causal calibration effect.** The code verifies a change in prompt emphasis and mandatory-choice ordering. It does not establish that `strengthen` or `reduce` causes a monotonic change in detected prevalence: the wording is qualitative, the per-defect quota is unchanged, model generation is stochastic, repairs can alter styles, and one category choice can displace another. The repository's focused tests verify the control path, not a controlled causal effect across LLM runs.

**Verified — units of work.** A *generation attempt* is one call to `provider.generate(task, 1, seed, specification)` for a submission slot, followed by validation and, on `PASS`, defect detection. A *functional repair attempt* is a subsequent generation attempt for the same slot with a revision request and a distinct repair seed; it can also be triggered by missing/extra styles when functionality already passes. A *calibration iteration* is a whole new `batch_size`-slot call to `run_iteration`, followed by aggregate comparison and possible feedback. Thus repair attempts affect one submission; calibration changes the next batch's guidance ([`workflow.py` lines 277–317, 333–441, 475–506](../services/generation/workflow.py#L277); [`experiment.py` lines 382–426](../services/generation/experiment.py#L382)).

## Differences from the conceptual framework and evidential limits

1. **Verified — calibration is qualitative and partly indirect.** Discrepancy actions change prompt wording and category-choice ordering; prevalence-to-quota probabilities are not updated. The quota draw is repeated with a new seed and the same empirical target. This is narrower than a numeric feedback update of assignment probabilities ([`experiment.py` lines 382–426](../services/generation/experiment.py#L382); [`assignment.py` lines 52–65](../services/generation/assignment.py#L52)).
2. **Verified — target quotas are not final assignment frequencies.** Mandatory category assignments can add zero-target defects and exceed planned counts/capacity; passing outputs can also contain unassigned defects. The observed profile measures detector outcomes, not guidance frequencies ([`workflow.py` lines 285–292, 394–403, 477–485](../services/generation/workflow.py#L285)).
3. **Verified — no explicit combination solver or runtime target eligibility filter.** Joint behavior is produced by load-balanced placement plus mandatory category choices, with task applicability checked for prompt choices. Pairwise style compatibility and arbitrary target keys are not validated ([`assignment.py` lines 70–103](../services/generation/assignment.py#L70); [`workflow.py` lines 252–270, 285–292](../services/generation/workflow.py#L252)).
4. **Verified — functional and style acceptance are distinct.** Functional `PASS` is enough to enter prevalence, even when the stricter style requirements fail; no minimum valid denominator gates profile acceptance. Non-regression gates selection of unaccepted batches only, and does not terminate the loop ([`analysis.py` lines 8–32](../services/generation/analysis.py#L8); [`workflow.py` lines 451–485](../services/generation/workflow.py#L451); [`experiment.py` lines 405–426](../services/generation/experiment.py#L405)).
5. **Partially Verified — recorded LLM outcomes do not validate the present loop.** The inspected 12 JSONL files contain 13 records and 19 iterative runs, all schema 1 or 2. Six historical iterative runs record `non_regressive_guard`, a stop reason absent from the current `run_experiment`, whose writer declares schema 3 and whose current stop reasons are `single_iteration`, `within_tolerance`, and `maximum_iterations` ([`experiment.py` lines 277–309, 375–432](../services/generation/experiment.py#L277); historical [`experiment-log-290926124333.jsonl` line 1](../research-notes/synthetic-generation-experiments/experiment-log-290926124333.jsonl#L1)). These logs corroborate that experiments were recorded, but cannot establish contemporary LLM response, monotonic convergence, or present-loop success rates. **Not Verified — empirical calibration effectiveness for the current implementation.**
